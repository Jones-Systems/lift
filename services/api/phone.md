## Native request and session contract

All routes are POST under `/api/auth`. Payloads are strict. Supply JSON and a fresh random `Idempotency-Key` (16–128 permitted characters, UUID recommended). Keep the same key and exact payload for an uncertain response; changing a code needs a new key.

| Route | Body and result |
| --- | --- |
| `/phone-number/challenge` | `{phoneNumber,binding}` → `{challengeId,phoneNumber,status,expiresAt,resendAfter}` |
| `/phone-number/resend` | `{phoneNumber,binding,challengeId}` → updated challenge view; never extends expiry |
| `/phone-number/verify` | `{phoneNumber,binding,challengeId,code}` → maintained library `{status:true,user,token}` plus signed `set-auth-token` |

Client must create `binding` with a cryptographically random 32-byte value encoded base64url (43 characters), preserve it only for this login attempt, and never log it, the code or session token. Challenge ID alone cannot check/resend. Phone payload is canonical international E.164 (`+` plus 8–15 digits, nonzero country prefix); explicit configuration additionally normalizes harmless formatting. National-number guessing is not implemented. Managed numeric codes are 4–10 digits.

There is no client `verified`, account ID, linking flag, `disableSession`, user field or provider endpoint input. Password phone login, raw send-OTP, password reset, number replacement and number release routes are excluded or closed. Strict guard rejects additional fields before the maintained verifier. Email/provider equality never merges accounts. Phone users have a reserved non-delivery `sha256(twilio-verify:E164)@phone.form.invalid` identity, an opaque library user ID, and a unique verified phone column. The same phone resolves the same subject; distinct phones and email registrations remain distinct. Existing domain account mapping derives only from the library session.

## Durable effects and unknown outcomes

Challenge lifetime is ten minutes, purpose is phone login only, and a secret binding hash protects the challenge. Each provider send/check has a durable `(challenge,operation,key,intent HMAC,status)` claim committed before network I/O. Only one check is in flight. Code/binding plaintext and provider credentials are never written to receipts. HMAC uses the stable server secret so a retained low-entropy OTP digest is not an offline guessing oracle.

Maximum three managed sends per challenge, minimum 30 seconds between resends, maximum five sends per phone per rolling hour, and maximum three checks per challenge. Limits survive restart. Resends do not reset attempts or expiry. Starting a different challenge waits ten minutes from the preceding send, including an unknown send; this conservatively avoids reusing an existing Twilio verification/code behind a fresh local budget. Better Auth also rate-limits `/phone-number*` to ten requests per minute in this pinned plugin. Retain database-backed auth rate limits in the parent.

Twilio Verify uses server API-key HTTP Basic authentication, the fixed HTTPS `verify.twilio.com` origin, form encoding, 15-second abort deadline, redirect rejection and a 16 KiB response bound. Sends use `/v2/Services/{VA}/Verifications` with `To` and `Channel=sms`; checks use `/VerificationCheck` with stored `VerificationSid` and submitted `Code`. The library-generated OTP is never sent or accepted as a fallback. Provider response account, service, destination and verification SID are checked before approval.

Only the check response’s `status:approved` can consume the challenge and reach library identity/session creation. Provider rejection is retained; replay does not retry it. Unknown transport, malformed/mismatched result, interrupted in-flight operation or unknown response is fail-closed. Restart observes durable claims; it does not resume outbound sends/checks. A `phone_outcome_unknown` response may mean an SMS was sent or an approval was consumed remotely. It does not establish a user/session locally.

Reconcile an unknown send/check using the retained operation/challenge and provider-owned evidence under separately authorized access. This module intentionally performs no automated status lookup, cancellation, approval update or blind retry: Twilio may delete approved/expired verification resources, so an unavailable resource is not an approval proof. Safe user recovery is a new bound challenge after the cooldown/provider lifetime. An expired challenge always rejects. Successful verification replay rejects with `phone_challenge_consumed`; a lost session response requires a new login, not another session issuance from the old proof. A process crash after provider approval or consumption can strand that attempt safely. Library identity/session writes are not claimed to be distributed-transactional with Twilio.
